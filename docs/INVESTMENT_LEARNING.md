# 기업 공부 private storage and API

The additive `/api/learning` router stores accounts and dated learning histories independently of watchlist sync and the existing Web UI. It never imports existing local research. The binding product/API specification is in the Toss repository at `docs/superpowers/specs/2026-11-01-investment-learning-design.md`.

## Durable setup

Set `LEARNING_DATABASE_URL` to a persistent PostgreSQL connection URL on the existing backend service. `DATABASE_URL` is accepted when a dedicated learning URL is absent. Use the provider's internal URL in the same network and its required TLS settings; do not place credentials in source, browser code, export files, URLs or logs. The database role needs permission to create the dedicated `learning_accounts`, `learning_sessions` and `learning_requests` tables and index on its first learning request. Market startup and `/health` do not connect to this database.

`GET /api/learning/status` reports `configured: true` only after a successful database connection/schema check. Missing or unreachable storage produces an explicit unavailable state; account/private operations return 503. It never falls back to browser-only or process-memory persistence.

For local verification only, set `LEARNING_SQLITE_PATH` to an explicit durable file path, for example an ignored scratch directory. PostgreSQL takes precedence. SQLite in-memory/URI paths are rejected, and all SQLite use is rejected if `RENDER`, `RENDER_SERVICE_ID`, `RENDER_EXTERNAL_URL` or `RENDER_INSTANCE_ID` is present. Production must use PostgreSQL; Render's ephemeral filesystem cannot retain private records across redeploys.

## Authentication and deletion

Account creation returns a server-generated 256-bit recovery key once, with a separate 256-bit bearer token. Recovery is possession based: the saved key creates a new bearer session; no email/password reset exists. Only SHA-256 hashes of these high entropy credentials are stored. Sessions expire after 30 days; `DELETE /auth` revokes the current token. `DELETE /account` with `{"confirmation":"DELETE"}` deletes the account, its document, sessions and idempotency receipts in a transaction. Device reset/log out clears the device credential and does not delete cloud records.

All learning responses, including authentication, malformed input, conflicts and errors, send `Cache-Control: no-store`. Protected routes verify the bearer session before reading any request body, including streaming imports; missing, invalid or expired credentials cannot trigger large-body buffering or JSON parsing. Database authentication runs in a worker thread and its verified identity is reused only within that request. Public lesson/catalog representations never expose correct answers. API errors use generic messages and do not echo submitted notes, bearer credentials or database connection details. Public account creation is limited to 10 requests per trusted client address per minute; recovery is limited to 30. This bounded per-process guard complements platform-level limits and does not retain raw addresses or credentials.

## Consistency and history

Each account has one durable versioned document. Every mutation checks `expectedVersion` while holding a PostgreSQL account-row lock (`BEGIN IMMEDIATE` locally). The document and idempotency receipt commit together. Successful UUID `requestId` retries return the current workspace plus the original stable `sessionId` (when applicable) and `requestVersion`, without applying the mutation again. Receipts retain only these identifiers/version and a request fingerprint, avoiding a full workspace copy on every save. Reusing an ID with different content or submitting a stale version returns 409. Clients retain unsaved drafts and explicitly reload/reconcile rather than silently overwriting.

The serialized account document is bounded at 128MiB; ordinary commands at 4MiB; import requests at 160MiB. Histories are never pruned automatically. This supports a year of ordinary daily notes; actual capacity depends on note lengths and save frequency, and a year at every field's maximum length is not guaranteed. The service refuses an oversized transaction atomically and keeps the prior account intact. These application limits are separate from the chosen database provider's storage quota. Enable provider storage monitoring before production use. Very large exports/imports also require enough server memory to parse and validate the full versioned document; future streaming/normalized storage is needed if unusual maximum-size usage becomes common.

Every note save appends a full session snapshot in `revisions` (`{id,sessionId,revision,session,createdAt}`). Lessons/questions are pinned on initial save in private server storage; curriculum edits affect later new studies. Editing a completed/evaluated record preserves its completion timestamp and actual attempt histories but requires valid required insights; saving creates a new revision and returns `completed` until that revision receives a real server-graded submission. Draft saves cannot create completion or quiz attempts.

Quiz/review submissions require all objective answers, written judgment, and a 0–4 evidence/logic/indicators rubric. The objective score is calculated from the pinned answer key. The separate judgment score is explicitly self assessed. Wrong answers include explanations after submission. Real KST submission date and objective score determine review dates (1 day below 60, 3 below 80, otherwise 7). Validation histories append evidence against a selected immutable revision; optional price context does not grade business reasoning.

## Backup and recovery

Authenticated `GET /export` returns a versioned `chartview-learning-backup` JSON document with no recovery key, token, hashes or private answer keys. Save it in private storage. `POST /import` validates the complete schema and cross-references before committing an additive merge. Conflicting IDs reject the entire import; existing live history is never wholesale replaced. A fresh version-0 account with no history adopts the backup's custom curriculum; an existing account preserves its current curriculum. Imported attempts carry `provenance: "imported"`; restored evaluations become `completed`, so imported scores never certify a new native evaluation. The original lesson/history remains readable. New native grading is available only when a restored public lesson exactly matches a reconstructable current content definition; unverifiable historical answer keys are never trusted.

Manual ChatGPT JSON import uses `format: "chartview-learning-result", schemaVersion: 1` with editable session fields and optional `externalAssessment: {score,notes}`. It creates a new dated record and labelled external assessment in `imports`; it cannot submit a native quiz or read any ChatGPT conversation/task.

Provider-level PostgreSQL backups are the operational disaster-recovery source of truth, including private pinned answer definitions and idempotency receipts. Enable and verify the database provider's backup/restore policy and access controls; user JSON exports are portable history backups. Before deployment, create a test learning record, verify its export privately, deploy only the exact tested backend revision, then recover/load that same record and confirm `/health.revision` and unchanged history. A successful Render build alone does not establish durable retention.

## Verification

Run `python -m pytest tests/test_learning_content.py tests/test_learning_service.py -q`. Set `LEARNING_TEST_DATABASE_URL` to a throwaway PostgreSQL database to run the same API contracts with actual PostgreSQL row locking, concurrency and rollback. The tests create/delete only their accounts in the dedicated learning tables; never point tests at a live customer database. Run the existing backend suite and generated frontend bundle check before release.
