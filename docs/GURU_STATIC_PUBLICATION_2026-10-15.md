# Same-version Guru evidence and bounded provisional responses

The Toss list is published to GitHub data before the manually deployed backend revision changes. A strict evidence API correctly returns409 during that interval. Keep that API contract and the existing manual Render operation. Do not add deployment hooks or fetch financial providers during evidence requests.

`publish_snapshot` now writes `static/data/guru_evidence/<snapshotVersion>/<symbol>.json` before publishing the aggregate evidence and list. The file contains exactly the candidate's existing evidence and snapshot/criteria/trade-date metadata. No screening conditions, calculations, PICK records or Web UI change. The workflow stages these files with the list in the same Git commit. Current and immediately preceding proof directories are retained; old versions fail closed rather than borrowing newer proof.

The coordinated Toss change tries its existing API first. Only HTTP409 permits loading a small proof for the exact displayed version. A wrong symbol/version or unavailable proof preserves the existing publication-waiting UI. Ordinary API success and non409 errors add no proof request. The first exported snapshot has135 unique candidate files, at most29,477bytes per file, copied from the saved bundle. Generated files do not imply a production deployment.

The provisional export endpoint previously awaited refresh/lock/thread completion without an overall response budget. It now waits at most20seconds for a shared refresh task. Shielding keeps one worker alive after callers time out; another caller cannot start duplicate provider work. A real cached response retains its original period and values with `cacheStatus=stale-error`; a cold timeout returns the existing503 error shape. The worker's eventual result can satisfy the next request. Existing provider timeout, TTL, source data and arithmetic remain unchanged. This is bounded recovery, not proof that every provider request is fast.
